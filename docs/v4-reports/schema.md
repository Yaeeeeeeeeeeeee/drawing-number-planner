# V4 Task 1: product identity and migration

Root causes: schema1 embedded `UNIQUE(brand_id, model)` and schema5 `products_sku_unique` blocked separate products with equal display strings. ProductService also translated these constraints into permanent business promises. Its referenced-meaning protection included `defaultAppearanceId`, incorrectly treating a planning default as historical identity. The explicit historical-candidate path independently rejected existing SKU strings and hid them from its candidate list.

Changes: migrate through schema19, remove only the two designated uniqueness constraints, preserve product identity columns and IDs, allow SKU/model duplicates, remove obsolete DB-error translations, allow referenced default changes while retaining all other referenced-identity checks. Explicit candidate confirmation permits existing SKU strings; it still requires exact unlinked historical tuple, rejects ambiguous/stale inputs, links only matching rows, and rejects replay once the rows are confirmed. No automatic merge or cleanup runs.

Schema19 creates `pdf_product_assignments` and `pdf_product_assignment_audit` with the agreed fields, positive revision and valid-JSON checks. Audit PDF references have no delete cascade.

Safety: existing migration backup occurs before changes. One outer transaction covers the entire legacy-to19 chain. Foreign keys are temporarily disabled before that transaction and restored in finally; this prevents products DROP from cascading into identity rows, while final explicit foreign_key_check enforces validity before commit. All old tables/rows are snapshotted and compared after the final ledger insertion (including trigger side effects), custom products indexes/triggers except products_sku_unique are replayed, and sqlite_sequence high water is restored. The original CREATE TABLE SQL is retained except its embedded brand/model constraint, preserving other columns/checks/FKs. Unknown/missing expected constraint aborts rather than guessing. Older v10 used implicit DROP-parent cascades to empty protected BOM asset/QR joins before restoring backups; with FK enforcement suspended, that exact cleanup is explicitly reproduced during its retained migration step. Existing old-version migration regression tests cover this compatibility path.
