# 图号规划器：资料批次、业务动线与交互修正 Design Document

**日期：** 2026-08-28  
**设计基线：** `master` / `86bc2fa4cfc4f0583aaedb95b32f91b39321ede5`  
**仅文档阶段：** 本文不授权代码实现、数据库迁移或 UI 修改。  
**已知前置修复：** 共享 API 空响应兼容性修复位于未合并分支 `codex/fix-empty-api-responses`，最终提交 `a616a37fb9c34b99778c938910759e877d8b2ac2`。

## 1. 目标与边界

本轮在不改变正式图号算法的前提下，建立“产品目录 → 资料批次 → PDF 文件实例 → 逻辑图号”的可靠关系，并改善图号库、PDF 文件中心、编码字典、产品档案和 BOM 的高频操作动线。

本轮不开发二维码、服务器同步、完整外发资料、自动打包、自动生成或覆盖 BOM、自动修改历史文件、全库自动重命名、多人权限或新的产品工作台。

以下既有规则保持不变：

- 完整图号结构、外观码、Excel 映射和图号解析；
- 历史图号永久占号；文件索引删除不得释放号码；
- 下一流水号推荐和查重算法；
- 资料根目录可配置，数据库保存相对路径；
- 历史扫描只读，不移动、删除或重命名磁盘资料；
- BOM 完整字段模型继续受真实 BOM 字段映射门禁约束。

## 2. 当前实现与真实数据调查

### 2.1 当前数据结构

- `drawing_numbers`：正式规划图号，一行代表一个逻辑图号。
- `historical_drawing_numbers`：可靠解析的历史已用图号，一行代表一个永久占号的逻辑图号。
- `pdf_files`：一行代表磁盘中的一个 PDF 文件实例；已保存 `relative_path`，并通过 `drawing_id` 或 `historical_drawing_id` 关联逻辑图号。
- `pdf_files.relative_path` 当前有精确字符串唯一约束，扫描使用 `ON CONFLICT(relative_path)` 更新同一路径记录。
- 当前 Schema 没有资料批次表，也没有 `pdf_files → 资料批次` 的持久关系。
- `historical_drawing_numbers` 只为一个图号保存一组检测产品信息；不能用它代替“同一图号在多个产品目录/批次出现”的文件实例关系。

结论：系统已经具备“图号”和“文件实例”的基础分离，不需要重构图号表；需要增加小范围批次模型。

- **图号库视角：** 428 个逻辑图号在同一产品目录的多个批次出现，对应 1,473 个合法文件实例；应聚合图号并展开批次。

T40 的七个批次均能从路径可靠识别；每个批次包含 15 个已匹配逻辑图号，最新编号批次是 `06.20260309`。`03.20250526` 等部分批次还包含未匹配的额外文件，因此“批次文件数”与“已匹配图号数”可以不同。

另有两个文件位于 `ZC200\...\预案\`。`预案` 没有正式顺序号，不能自动当作当前有效批次，应进入批次待确认状态。

### 2.3 真正重复与合法重复

定义如下：

- **文件实例唯一键：** 资料根目录内经过 Windows 规则归一化的相对路径。
- **真正的扫描重复：** 两条 `pdf_files` 记录拥有同一个归一化相对路径。
- **合法跨批次重复：** 相同图号或相同文件名位于不同批次路径；必须全部保留。
- **同批次多实例：** 同一图号在同一批次也可能因型号变体、源文件/转曲文件或历史整理方式出现多份文件；仍按不同相对路径保留并展示，不能仅凭图号删除。

文件名、图号、文件大小、修改时间或文件内容哈希都不能作为 V1 的删除依据。

### 2.4 共享 API 和“停用无反应”根因

当前 master 的共享客户端对所有响应无条件调用 `response.json()`。桌面后端重启期间，Vite 代理实际可能返回空 body 的 502；因此真实 UI 会出现 `Unexpected end of JSON input`，网络失败还会泄漏 `Failed to fetch`。原测试只模拟 JSON response，所以没有覆盖真实代理行为。

该问题已经在隔离分支 `a616a37` 修复并通过 299 项测试、类型检查、浏览器/桌面构建和真实后端中断验证，但尚未进入 master。本轮实现的第一前置步骤应先把该小范围修复纳入新的实施分支，并保留独立审查记录。

停用操作还有第二个可用性问题：当前无行内忙碌状态，错误提示位于整页底部。列表较长时，即使后端返回错误，用户也会认为按钮没有反应。本轮需增加行内“处理中/成功/错误”反馈，但不在各页面重新实现 response 解析。

### 2.5 其他模块现状

- `DataTable` 只支持单行，没有选中行后的展开区域；编码字典编辑器和图号详情只能出现在表格之后。
- 产品历史候选确认表单位于全部候选卡片之后，而不是所选候选下方。
- 产品查询已有搜索、品牌、状态，没有产品类别精确筛选；类别数据已存在于 `products.product_category`。
- 层数使用独立 `layer_count` 类型，从 Excel 独立列导入，不参与正式图号字符串；可完全只改 UI。
- 字典没有删除 API。现有引用检查只覆盖部分正式表，没有覆盖历史图号编码快照、BOM 和主类别子项。
- BOM 当前仍以 `(product_id, color_id)` 为当前键，`quantity` 必填，只有 `created_at`，没有业务变更日期。

## 3. 方案选择

### 方案 A：每次查询时只从 `relative_path` 临时解析批次

优点是没有 migration。缺点是无法稳定保存批次识别状态、无法把待确认批次与有效批次分开，也不能为 BOM/外发资料提供可靠关系，不满足“保存批次与文件实例关系”。不采用。

### 方案 B：把批次名称、顺序和产品目录重复写入每一条 `pdf_files`

实现较快，但同一批次元数据会重复数十次，批次状态和当前批次判断容易不一致。后续查询和确认操作也会变复杂。不采用。

### 方案 C：新增小型 `material_batches` 表，并让文件实例可选关联批次

该方案保留现有图号表和 `pdf_files`，只新增批次实体和一条外键关系。批次解析集中在文件领域，图号库、PDF 文件中心以及未来 BOM/外发资料读取同一事实来源。采用此方案。

## 4. 资料批次模型

### 4.1 关系

```text
产品档案（可为空，历史候选仍可识别）
  └─ 产品目录身份：{产品类别}\{SKU}-{型号}
       └─ 资料批次：03.量产后的变更文件...\{批次目录}
            └─ PDF 文件实例：pdf_files.relative_path
                 └─ 逻辑图号：drawing_numbers 或 historical_drawing_numbers
```

一个逻辑图号可以关联任意多个文件实例；一个文件实例最多属于一个资料批次。没有进入批次目录的源文件仍保留 `material_batch_id = null`。

### 4.2 `material_batches` 字段

建议 Schema v6 新增：

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `relative_path` | 批次目录相对资料根目录的路径，大小写不敏感唯一 |
| `product_directory` | 前两级产品目录相对路径 |
| `product_id` | 能唯一匹配正式产品时关联，否则为空 |
| `detected_product_category` | 从目录读取的类别 |
| `detected_sku` / `detected_model` | 能可靠解析时保存，否则为空 |
| `name` | 批次目录原名 |
| `sequence_number` | `00`、`01`、`02` 等顺序；遗留无编号 `首批大货` 记为 0 |
| `business_date` | 名称中仅有一个可靠 `YYYYMMDD` 时保存 ISO 日期，否则为空 |
| `recognition_status` | `recognized` 或 `pending` |
| `classification_warning` | 顺序/日期/目录歧义说明 |
| `is_present` | 当前磁盘是否仍存在该批次目录 |
| `first_seen_at` / `last_seen_at` | 首次和最近扫描时间 |

`pdf_files` 增加可空 `material_batch_id`。同时增加应用生成的 `path_key`，内容为统一反斜杠并按 Windows 规则转小写的相对路径；`path_key` 建唯一索引。原 `relative_path` 继续保留用于展示和迁移资料根目录。

### 4.3 识别规则

仅把 `03.量产后的变更文件...` 的**直接子目录**识别为批次；直接放在 `03...` 下的 PDF 不是批次。

- `NN.<任意非空名称>`：可靠批次，`sequence_number = NN`。
- 遗留目录名完全等于 `首批大货`：可靠批次，`sequence_number = 0`。
- `预案` 或其他无编号名称：登记为 `pending`，不参与当前批次判断。
- 名称中只有一个有效八位日期：提取为 `business_date`。
- 名称包含多个日期、非法日期或顺序冲突：保留原名并记录 warning，不猜测日期。
- 同一产品目录下最高顺序出现多个批次：当前批次为“待确认”，不自动选择。

扫描仍为只读。重扫会更新批次/文件索引，不移动、删除、重命名任何目录或 PDF。

## 5. 当前使用判断

### 5.1 当前有效资料批次

对每个 `product_directory`：

1. 只考虑 `is_present = 1` 且 `recognition_status = recognized` 的批次；
2. 取最大的 `sequence_number`；
3. 最大顺序只有一个批次时，它是当前有效批次；
4. 没有可靠批次或最大顺序并列时，状态为待确认；
5. `business_date` 用于展示和异常校验，不取代顺序号；禁止使用 PDF 修改时间。

该规则符合历史目录“每个批次保存变更后整套实际资料快照”的语义。系统不在相邻批次之间自动补齐缺失文件。

### 5.2 图号使用状态

以“产品目录 + 完整图号”为粒度判断：

- **当前使用：** 当前有效批次内至少有一个已存在、可靠匹配该完整图号的文件实例。
- **历史使用/已替换：** 旧批次内出现，但当前有效批次内没有出现。
- **未纳入批次：** 只有批次外文件实例。
- **待确认：** 产品目录没有唯一当前批次，或文件未能可靠匹配图号。

图号的业务状态（已占号/正式使用/作废）和批次使用状态相互独立。作废图号仍永久占号；如果作废图号出现在当前批次，UI 显示冲突提示，但不自动修改图号或批次。

一个图号可能在某产品当前使用、在另一产品仅历史使用。图号库默认展示“当前用于 N 个产品 / 历史用于 M 个产品”；在 SKU/型号或资料批次上下文中才显示单一的当前/历史结论。

## 6. 图号库和 PDF 文件中心

### 6.1 图号库

图号库保留现有完整组合筛选，增加二级视图：

- **按图号：** 一行一个逻辑图号，显示业务状态、当前/历史使用摘要、出现批次数、源文件/转曲后完整性；展开后按产品目录和批次列出全部文件实例。
- **按资料批次：** 搜索 SKU/型号/产品目录，先显示当前批次与历史批次；展开批次后显示该目录内全部已匹配、待确认和未匹配 PDF。

“打开最新文件”表示打开当前有效批次内相应类型的文件；若无唯一当前批次则禁用并说明原因。用户仍可在批次明细中打开任意历史文件位置。

### 6.2 PDF 文件中心

PDF 文件中心继续逐文件实例展示，不按图号去重。增加批次名称/批次状态筛选与说明：

- 跨批次相同图号是合法历史快照；
- 真正重复诊断只按 `path_key`；
- 缺失索引清理只删除 `pdf_files`，不删除 `material_batches` 的历史识别信息，也不删除历史占号；
- 批次目录消失后 `is_present = 0`，可在后续明确的批次清理操作中清理索引，但不释放图号。

导航中 PDF 文件中心从“日常工作”移动到“基础资料”。

## 7. 就近展开交互

扩展通用 `DataTable`，支持在指定记录 `<tr>` 后渲染一个跨列展开行。该能力只负责布局，不持有业务状态。

应用范围：

- 编码字典：改名、行内请求状态、删除二次确认在对应记录下展开；
- 产品档案：现有产品编辑在对应行展开；新建产品仍可使用页面顶部创建区；
- 历史产品候选：确认表单直接渲染在所选候选卡片内；
- 图号库：图号详情和批次/文件实例在所选图号后展开；
- 其他页面只在确实存在“点击某行、表单出现在列表末尾”的模式时采用，不把普通筛选或批量工具栏改成行内表单。

## 8. 编码字典

### 8.1 层数 UI

顶部仍只有品牌、品类尺寸、外观、颜色、主类别。主类别页面保留主从布局，右侧详情区增加“项目明细 / 层数”局部切换；层数不再占据第三个大板块。

底层 `layer_count`、Excel 导入列和全部图号算法不变。

### 8.2 删除与停用

新增 `DELETE /api/dictionaries/items/:id`。删除前由服务层统一检查：

- 产品对品牌、品类尺寸、默认外观的引用；
- 正式图号的外观、颜色、主类别、项目明细引用；
- 历史图号的编码快照引用；项目明细按“主类别码 + 项目明细码”判断；
- BOM 的颜色和项目明细引用；
- 主类别是否仍有项目明细子项；
- 其他现有外键业务引用。

从未使用且无子项的编码允许物理删除。任何历史或业务引用返回 `DICTIONARY_ITEM_REFERENCED`，提示用户改用停用。删除采用行内二次确认。

停用继续保留历史解释；所有新建产品、图号规划和 BOM 候选默认只加载 active 字典项，查询历史时可包含 inactive。

## 9. 产品档案与导航

- 产品筛选增加 `productCategory` 精确条件；选项直接从已加载产品档案的现有类别去重，不新增字典表。
- 历史候选确认区移动到对应候选卡片下。
- 导航调整为：日常工作 = 图号规划、BOM 管理、外发资料（未开放）；基础资料 = 图号库、产品档案、PDF 文件中心、编码字典、迁移检查。
- 不新增产品工作台。

## 10. BOM 门禁和本轮可做范围

### 10.1 不需要 Schema 的部分

- BOM 页面拆成“添加 BOM / 查询 BOM”两个局部 Tab；
- 添加页不再同时堆叠历史记录；
- 数量输入从 UI 移除，现有兼容字段固定发送 1；
- 查询页可按型号、项目、图号查询现有保存记录；
- 备注继续在当前和历史明细中展示；
- `created_at` 只标为“系统保存时间”。

### 10.2 受门禁暂缓的部分

以下不能在没有真实 BOM 字段映射确认时实施：

- 新增并持久化 `business_change_date`；
- 把 `bom_current` 从 `(product_id, color_id)` 改为只按产品；
- 从 Schema 删除 `quantity`、`color_id` 或重构现有 BOM 表；
- 用资料批次自动生成、覆盖或修正 BOM。

业务变更日期不能用 `created_at` 冒充。字段映射确认后，应另行批准一个窄 migration；在此之前查询页只显示“系统保存时间”，不提供伪业务日期筛选。

## 11. Schema 影响清单

### 不需要 Schema 修改

- 共享 API client 修复；
- 行内展开和行内错误反馈；
- 产品类别筛选；
- PDF 导航位置；
- 层数 UI；
- 字典安全删除服务和接口；
- BOM 添加/查询 UI 拆分、隐藏数量输入并固定兼容值 1；
- 图号解析、查重、流水号和历史占号保持不变。

### 需要小范围 Schema v6 migration

- 新增 `material_batches`；
- `pdf_files.material_batch_id`；
- `pdf_files.path_key` 及唯一索引，用于同一实际路径幂等扫描；
- 批次和文件关系的必要索引。

迁移前必须生成并校验数据库备份；迁移事务内回填 2,666 条现有路径的 `path_key`，验证无重复、文件行数不变、外键检查通过。批次数据不在 migration 中猜测回填，首次修复版扫描时从磁盘只读识别并写入。

### 因 BOM Schema 门禁暂缓

- BOM 业务变更日期；
- BOM 顶层颜色键调整；
- 删除 BOM 数量字段；
- 真实 BOM Excel 的其余字段。

## 12. 错误处理和安全

- 浏览器和 Electron 继续共用一个 API client；不得在页面重复解析 response。
- JSON、空 body、204、非 JSON、非 2xx、网络中断和 token 刷新由共享层统一处理。
- 写操作显示行内忙碌和明确结果；重复点击在请求完成前禁用。
- 扫描失败保持上一次索引和批次关系不变。
- 批次识别歧义进入 pending，不猜测当前批次。
- 删除字典和清理文件索引均二次确认；历史图号表不提供删除路径。

## 13. 验收标准

1. T40 能显示七个资料批次，`06.20260309` 为当前有效批次。
