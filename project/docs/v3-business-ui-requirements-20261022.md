# 图号规划器｜全局业务修正与 UI 优化需求 V3.0

**开发对象：Codex**
**实施方式：现有项目增量修改，不重新开发**
**最高优先级：修复图号库历史图号与产品关联失败的问题**
**修改范围：图号库、产品档案、PDF 文件中心、外发资料、二维码管理、侧边栏、全局 UI**

## 一、总体要求

本次修改以简化实际操作、修复数据关联、统一视觉设计为目标。

不要继续增加不必要的业务概念、状态、审核步骤及操作入口。

核心原则：

1. 优先修复现有功能，不重复开发相同功能。
2. 充分复用现有编码字典、产品档案和 PDF 扫描结果。
3. 取消新增的独立外观版本管理机制及其冗余界面。
4. 保留原有图号编码规则中的外观编码。
5. 保留所有历史正式图号和历史占号。
6. 不删除真实 PDF 文件。
7. 不破坏 BOM、外发历史和其他历史引用。
8. 统一所有页面的对齐、间距、字体、状态标签和操作布局。
9. 页面以业务数据为主，删除不必要的说明小字。
10. 不要因为本次修改而增加新的管理功能。

开发前先阅读项目 Skill 及其指向的必要业务、Schema、数据安全文档，检查当前代码与数据库结构。

需要修改代码、迁移和测试的内容可在隔离开发环境中一次完成，不必逐个阶段等待确认。涉及真实业务数据的不可逆操作不能在应用启动时自动执行。

# 二、P0：优先修复图号库关联失败

## 2.1 当前问题

这是本次开发最重要的问题。

当前数据库中，图号库显示：

- 758 条历史图号。
- 来源为历史扫描。
- 关联产品显示「待关联」。
- 大量记录没有产品关联。
- 历史图号仍显示使用中。

但是，在 PDF 文件中心：

- 能识别完整图号。
- 能识别产品 SKU。
- 能识别产品型号。
- 能识别产品类别。
- 能识别对应 PDF。
- 能识别资料批次。

产品档案也已经创建，并在创建时选择了：

- 品牌
- 品类尺寸
- 默认外观编码
- SKU
- 型号
- 产品类别

同一份数据在 PDF 文件中心可以识别，在图号库却不能正确关联。

这导致图号库无法正常按照产品管理历史图号，也影响后续 BOM、文件对应关系和外发核对。

## 2.2 不要直接猜测根因

先检查现有代码和数据库。

重点排查：

1. PDF 文件中心的产品识别依据是什么。
2. 图号库的产品关联依据是什么。
3. 两个模块是否使用相同产品 ID 和完整图号。
4. 历史图号记录中的产品关联字段是否为空。
5. 是否存在关联数据但图号库查询没有读取。
6. 历史扫描时是否只保存占号记录，没有保存产品关联。
7. 是否在新增产品后缺少对应的历史关联更新。
8. 是否因新增的独立外观版本逻辑导致关联条件不匹配。
9. 图号解析是否正确拆分品牌码、品类尺寸码、外观码、颜色码、主类别码和版本流水号。
10. 是否存在扫描识别与正式图号规划采用不同关联规则的问题。

不得在没有定位原因之前，对 758 条图号直接执行强制关联。

## 2.3 正确的关联依据

图号编码规则保持不变：

`品牌码.品类尺寸码.外观码+颜色码.主类别码+项目明细码+版本流水号`

例如：

`02.0305.010.0201001`

`02.0305.020.0201001`

这两个图号的外观编码不同，属于不同外观编码范围。

产品档案已经保存品牌、品类尺寸以及用于初始规划的外观编码。

因此，系统应该充分利用这些信息。

关联时优先结合：

1. 完整图号。
2. PDF 文件中心已确认的产品关联。
3. 产品 ID。
4. SKU。
5. 型号。
6. 品牌编码。
7. 品类尺寸编码。
8. 外观编码及颜色编码。
9. 文件关联批次。
10. 已有人工确认关系。

注意：

**品牌码 + 品类尺寸码 + 外观码，不一定能唯一识别某个 SKU。**

因此，不能仅凭相同编码前缀，将全部历史图号关联到某一个产品。

PDF 文件中心显示的型号、SKU 如果只是从目录名推测，也不能直接视作已确认关系。

必须识别可靠的产品关联依据。

## 2.4 修复要求

- 优先复用 PDF 文件中心已有的可靠产品关联。
- 同一个完整图号关联到唯一产品时，图号库应显示同一个产品。
- 历史图号能够唯一确认归属时，补全其关联关系。
- 图号库左侧产品树应能展示对应历史图号。
- 图号库主表的关联产品只显示型号，例如 `ZU70SD`。
- 不要求用户重新创建产品。
- 不要求用户逐条手动关联可自动确认的历史图号。
- 不新增独立的图号识别系统。
- 不新增第二套产品关联数据。
- 不因后续扫描丢失已经确认的关联。
- 关联冲突时，保留原始数据，不强制指定产品。

如果问题只是查询没有读取现有关系，应修复查询，不应重复写入关系。

如果问题是历史数据缺少关系，则在备份、验证和审计的前提下修复可确认的记录。

## 2.5 占号安全

无论历史图号是否关联成功：

- 已经使用过的图号继续永久占号。
- 不得重新分配。
- 不得修改原图号。
- 不得重置版本流水号。
- 不得因删除文件索引释放图号。
- 不得破坏历史 BOM。
- 不得破坏旧外发记录。

图号的产品关联和图号占用是两个不同概念。

## 2.6 必须输出的排查结果

开发完成后，单独报告：

- 实际根因。
- 修复前历史图号总数。
- 修复前已关联数量。
- 修复前未关联数量。
- 修复后已关联数量。
- 修复后未关联数量。
- 无法关联的主要原因。
- 是否发现错误关联。
- 是否修改数据库。
- 是否影响图号占用。
- 自动化测试结果。

不能只报告「已优化关联逻辑」。

## 2.7 验收标准

对于 PDF 文件中心已经可靠确认所属产品的历史图号，图号库也应该正确显示该产品。

例如：

```text
PDF 文件中心
完整图号：02.0305.010.0201001
产品：ZU70SD
SKU：SKDZU070JP

图号库
完整图号：02.0305.010.0201001
关联产品：ZU70SD
```

只有确实无法确认或存在冲突的记录才继续显示「待关联」。

# 三、P0：取消独立外观版本管理

## 3.1 取消的概念

此前新增了：

- 初始外观
- 当前使用外观
- 历史外观状态
- 独立外观版本档案
- 外观版本使用状态
- 产品与外观版本关联修正
- 沿用到外观版本
- 外观待确认 / 使用未确定

这些概念增加了操作复杂度，与原有编码字典存在重复。

**本次要求取消这些独立管理概念在用户界面中的操作。**

不要继续要求用户创建、选择或维护另一套外观版本。

## 3.2 保留原有外观编码

原有编码字典中的外观码必须保留。

例如：

`02.0305.010.0201001`：1 号外观编码范围。

`02.0305.020.0201001`：2 号外观编码范围。

外观改变时，通过原有编码字典选择新的外观编码规划图号。

同一个外观编码范围内，具体包材发生修改时，按照原有版本流水规则规划新图号。

旧外观不再用于新生产，但所有历史图号、PDF、BOM 和外发历史继续保留。

不需要单独设置哪个外观当前使用。

## 3.3 产品档案调整

取消产品档案中后来新增的独立外观版本管理入口。

新建产品时原有的外观编码选择，仍可作为图号规划所需的编码信息使用。

但不能因此再自动创建一个无实际意义的「初始外观」管理对象，要求用户单独维护。

如果数据库已有外观版本字段或历史记录：

- 先检查代码依赖。
- 不直接删除表或字段。
- 不破坏历史引用。
- 可通过兼容层保留旧数据。
- 前端取消重复管理入口。

## 3.4 图号库详情调整

移除以下不再需要的业务操作入口：

- 产品与外观关联修正中的独立外观选择。
- 沿用到外观版本。
- 当前使用外观设置。
- 历史外观状态设置。

但保留必要的产品关联修复机制和历史审计数据。

不允许把取消冗余外观 UI 理解为删除产品关联、历史图号归属或编码字典。

# 四、P0：PDF 文件中心产品与批次树

## 4.1 取消初始外观空节点

目前左侧目录树存在：

```text
F20
├── 初始外观  当前使用  0
├── 20250310
├── 20240511
└── 首批大货
```

其中「初始外观」是空节点，没有实际业务价值。

要求取消该节点。

对于一个产品的正常批次展示：

```text
F20
├── 首批大货
├── 20240511
└── 20250310
```

如果确有多个不同外观编码的资料，需要区分时，可以按原有外观编码组织显示，例如 01 号外观、02 号外观。

但这种分组仅表示编码归属，不引入独立外观版本状态和管理流程。

## 4.2 批次状态

取消：

- 使用未确定
- 外观待确认
- 当前使用外观

批次只需要：

- 当前批次
- 历史批次

同一产品下如果需要按外观编码分组，各编码分组分别判断当前批次。

例如：

```text
ZC100
├── 01号外观
│   ├── 首批大货    历史批次
│   └── 20250510    当前批次
└── 02号外观
    ├── 首批大货    历史批次
    └── 20251020    当前批次
```

各组的最新有效批次可以同时显示「当前批次」。

这里的当前批次代表该编码分组下最后一套有效资料，不表示旧外观仍然在生产。

批次先后应优先采用可靠的业务批次顺序或日期，不得凭 PDF 文件修改时间随意判断。

无可靠顺序时，应保留原有批次，不擅自修改历史归属。

## 4.3 批次改名入口

目前同一功能出现两次：

- 左侧批次旁的编辑图标。
- 右侧文件行「更多」中的批次改名。

要求：

**保留左侧编辑图标，删除右侧重复的批次改名。**

批次改名只修改系统显示名称，不修改磁盘文件夹名、PDF 文件名或旧外发快照。

# 五、P0：PDF 索引与图号占用安全

## 5.1 清除索引

清除 PDF 索引不等于删除原始 PDF。

要求检查现有操作是否满足：

- 不删除磁盘 PDF。
- 不释放正式图号。
- 不释放历史图号。
- 不删除历史 BOM 引用。
- 不删除外发历史。
- 不破坏必要的历史文件关联记录。

对受保护记录必须遵守项目原有数据安全规则。

**本次不增加新的清除索引功能、不增加新的处理模式或复杂确认流程。**

只核查并修复当前实现中的错误。

## 5.2 暂不纳入

保留现有「暂不纳入」功能及其恢复能力。

原始 PDF 保留。

重新扫描不能无故取消排除状态。

历史外发和图号占用不受影响。

# 六、P1：图号库详情抽屉重新设计

这是本次重点 UI 改造页面。

## 6.1 当前问题

现有详情页面包含大量连续板块：

- 图号信息
- 产品信息
- 外观关联修正
- 沿用到外观版本
- 业务状态
- 关联依据与占号
- 关联修正记录
- 源文件
- 转曲后文件
- 历史文件
- 关联批次
- PDF 出现位置
- 当前 BOM
- 历史 BOM
- 危险操作

全部纵向排列，间距不统一，视觉上拥挤杂乱。

需要合并重复内容，并通过独立浅色底框建立视觉层级。

## 6.2 建议新结构

详情抽屉划分为五个区域：

### 顶部：图号信息

显示：

- 完整图号
- 复制图号
- 图号状态
- 来源
- 关闭按钮

取消重复的完整图号展示。

### 01 基础信息

包含：

- SKU
- 型号
- 品牌
- 产品类别
- 主类别
- 项目明细
- 可从编码中可靠识别的外观码信息（如确有必要）

采用双列网格，标签和内容统一对齐。

不显示独立外观版本状态。

### 02 文件信息

包含：

- 源文件
- 转曲后文件
- 历史文件

每类文件采用统一文件卡片。

文件存在状态在右上角显示一次。

文件名默认单行，空间不足时显示省略号。

路径默认折叠或使用简短路径展示。

提供打开文件位置的原有操作。

不重复显示「已有」「当前存在」。

### 03 业务关联

包含：

- 关联产品
- 关联批次
- PDF 出现位置
- 当前 BOM
- 历史 BOM

如果存在多个 PDF 文件实例，应能查看其分别属于哪些批次。

不要把「PDF 索引中出现」直接等同于「业务已使用」。

低频信息默认折叠。

### 04 关联维护

仅保留确实必要的产品关联维护和历史关联审计。

删除独立外观版本相关入口。

没有关联修正记录时，不显示一个占据空间的空板块。

### 05 其他操作

包含：

- 现有合法状态操作
- 必要的安全操作
- 删除图号等危险操作

危险操作与普通操作明确分开。

不改变现有历史占号保护规则。

## 6.3 背景框颜色

使用浅灰色背景框区分板块。

建议：

- 页面基础背景：白色。
- 分组卡片背景：`#F7F8FA` 或接近的现有设计色。
- 卡片边框：浅灰色。
- 圆角：8–10px。
- 标题：深色，加粗。
- 标签：中性灰。
- 状态颜色：沿用项目现有体系。

不使用大量彩色背景。

危险操作可以采用淡红色边框或文字强调，但不能让整个详情页面充满颜色。

## 6.4 间距要求

统一使用：

| 元素 | 建议间距 |
|---|---|
| 主板块之间 | 20–24px |
| 卡片内部 | 16–20px |
| 标题与内容 | 12–16px |
| 字段标签与值 | 4–8px |
| 同组字段 | 12–16px |
| 按钮之间 | 8–12px |

间距应通过统一组件和样式变量实现，不要每个板块单独硬编码不同规则。

## 6.5 抽屉宽度

在宽屏环境下，详情抽屉建议宽度为 600–680px。

较窄窗口下自适应。

不能出现：

- 文件名被逐字换行。
- 按钮挤压。
- 状态标签错位。
- 两列内容相互覆盖。
- 标题与内容紧贴。
- 多个按钮不对齐。

# 七、P1：PDF 文件中心顶部与表格

## 7.1 压缩顶部扫描区域

目前顶部包含：

- 资料根目录
- 扫描按钮
- 多项索引统计
- 本次扫描变化
- 恢复默认宽度
- 长说明文字

占用过多垂直空间。

修改为：

**单行紧凑工具栏 + 按需展开扫描详情。**

默认显示：

- 当前目录
- PDF 总数
- 未匹配数量
- 扫描资料库按钮
- 详细信息展开入口

原有保存目录、扫描统计和变化详情应通过现有操作或展开区域访问。

目标是减少顶部高度，而不是删除实际扫描功能。

## 7.2 表格优化

- 文件名优先分配列宽。
- SKU、型号、图号不强制换行。
- 批次、文件状态、匹配状态居中。
- 操作按钮组整体居中。
- 表头与数据列严格对齐。
- 尽量取消文件名因列宽不足产生的多行折行。
- 保留长文件名查看能力。
- 减少重复状态和长说明列。
- 表格充分使用剩余高度。

## 7.3 取消传统分页

PDF 文件中心取消：

- 每页数量选择器
- 上一页
- 下一页
- 第几页

保留文件列表滚动。

大量文件通过自动分批加载或虚拟列表提高性能。

不能一次渲染数千条 DOM 导致卡顿。

勾选状态、筛选条件和滚动位置需要合理保持。

# 九、P1：二维码管理 UI 优化

## 9.1 产品主列表

重新整理主列表：

| 字段 | 对齐 |
|---|---|
| SKU | 左 |
| 型号 | 居中 |
| 产品类别 | 居中 |
| 说明书 | 居中 |
| 售后卡 | 居中 |
| 菜谱 | 居中 |
| 操作 | 居中 |

保留必要产品信息。

不显示重复的「二维码数量 0」「文件关联 0/0」等统计列。

产品仍可展开查看二维码用途。

## 9.2 展开用途行

使用：

`用途｜关联文件｜网址｜业务状态｜操作`

具体要求：

- 用途居中。
- 关联文件左对齐。
- 网址居中。
- 状态整体居中。
- 操作按钮组整体居中。
- 统一行高。
- 统一 12px 左右的单元格水平边距。
- 文件名过长时单行省略。
- 避免嵌套表格的边框过多。

只保留需要的操作入口。

不要为每个状态增加重复说明。

## 9.3 二维码文件关联

沿用人工选择 PDF 的工作方式。

不恢复自动候选匹配或待人工确认扫描流程。

已有文件显示「更换文件」，未关联文件显示「关联文件」。

其他二维码属性在详情中管理。

## 9.4 修复 PDF 文件名校验

已出现以下实际问题：

`B500-warranty（hwh0kd9）.pdf`

网址为：

`https://qrs.ly/hwh0kd9`

文件名结构与业务信息匹配，却被提示校验失败。

要求检查现有解析逻辑。

需要兼容：

- `Warranty` 和 `warranty`
- `User Manual` 的合理大小写差异
- `Recipe` 的合理大小写差异
- 全角括号 `（）`
- 半角括号 `()`
- 括号前的合理空格
- URL 末尾路径段的 7 位尾码

例如以下文件均应可以正确识别：

```text
B500-Warranty（hwh0kd9）.pdf
B500-warranty（hwh0kd9）.pdf
B500-Warranty(hwh0kd9).pdf
B500-warranty (hwh0kd9).pdf
```

必须核对型号、用途及网址尾码。

不能因大小写或括号形式不同而拒绝。

对于 `H10-warranty-avakyo（g8gwcl6）.pdf` 这类含额外名称的历史文件，应检查现有例外关联机制，允许用户在确认身份后按现有规则处理，不强制修改原始 PDF。

不要新增另一套例外审批系统。

## 9.5 关联弹窗

简化布局，重点突出：

- 产品及用途
- 当前网址
- 选择 PDF
- 校验结果
- 确认关联

既有必要信息可以保留，但不要一次堆满大量辅助字段和说明。

# 十、P1：外发资料模块修正

外发资料业务以此前确认的真实工作流程为准。

## 10.1 实际文件管理方式

每次包材更新，新建一个资料文件夹。

新文件夹同时包含：

- 未修改的旧资料
- 已修改的新资料

因此新批次本身就是一套新的完整包材资料。

系统不需要默认跨所有历史批次重新拼装完整文件。

## 10.2 选择区域简化

删除：

- 产品搜索输入框
- 独立外观版本下拉框
- 对比基准下拉框
- 人工指定跨外观比较复选框

只保留：

- 品牌
- 产品
- 资料批次
- 资料类型
- 打包范围

这些字段采用整齐的三列布局。

输入框和下拉框统一高度。

## 10.3 资料类型

资料类型应支持：

- 首批资料
- 更新资料

允许用户选择。

不能因 BOM 未维护或图号库历史图号未关联而禁用。

如果资料类型当前无法选择，必须检查真正的禁用条件与批次加载逻辑。

## 10.4 完整包材资料

选择完整包材时：

- 读取指定批次的转曲后 PDF。
- 默认只从选定批次取文件。
- 不自动拼接不同历史批次。
- 不要求先维护 BOM。
- 有异常时明确提示。
- 最终用户确认。

## 10.5 本次变更资料

选择本次变更时：

- 自动对比所选批次与可靠确定的上一批次。
- 默认推荐新增、修改文件。
- 未变化文件默认不选。
- 无法可靠对比时提示原因。
- 不擅自跨外观编码比较。
- 保留人工调整勾选能力。

## 10.6 外发页面布局

继续采用四段全宽纵向结构：

1. 选择外发范围
2. 外发文件清单
3. 生成外发结果
4. 邮件草稿

取消原来左侧拥挤文件清单、右侧大面积空白的布局。

外发文件表格要求：

- 文件名左对齐。
- 图号居中。
- 来源居中。
- 状态居中。
- 操作居中。
- 删除大段常驻说明列。
- 长文件名默认单行。

## 10.7 ZIP 分包

保留现有压缩包命名规则。

每个 ZIP 必须显示：

- 压缩包名称
- 文件大小
- 实际文件数量
- 查看路径或打开位置

不允许显示「文件数量未提供」。

各分包文件数之和必须等于实际打包文件数。

ZIP 打包后保存实际文件明细和不可变的外发历史。

## 10.8 BOM 的作用

BOM 只做辅助核对。

未维护 BOM 的产品仍然可以外发。

已维护 BOM 时可用于检查文件遗漏、图号不一致等情况。

不能把 BOM 未维护直接认定为文件不能使用。

# 十二、P1：全局 UI 强制规范

这部分适用于整个图号规划器，而不仅是本次截图涉及的页面。

## 12.1 核心设计原则

**整齐、舒适、对齐、对称、间距合理、不拥挤。**

不能为了显示更多数据，把文字、按钮和标签挤压在一起。

也不能为了留白而浪费大量空间。

## 12.2 文字对齐

统一原则：

- SKU、文件名、路径、较长文本：左对齐。
- 型号、日期、数量、状态：按列统一居中。
- 操作按钮组：整体居中。
- 表头必须与对应数据对齐。
- 同类字段跨页面保持相同的对齐方式。

不允许出现表头居中、数据却偏左的情况。

## 12.3 不强制换行

默认单行显示：

- 图号
- 文件名
- SKU
- 型号
- 日期
- 批次名称
- 状态
- 操作按钮

宽度不足时：

1. 优先合理调整宽度。
2. 仍不足时显示省略号。
3. 悬停可查看完整内容。

不要出现中文逐字竖排、按钮文字断行、数字编码被拆断等问题。

邮件正文、长备注、完整错误解释可自然换行。

## 12.4 页面间距

建议统一基础间距尺度：

- 4px
- 8px
- 12px
- 16px
- 20px
- 24px

主要区域之间优先采用 20–24px。

普通表格单元格水平内边距优先为 12px。

同一行控件统一高度。

避免局部随意设置过大的 margin 或 padding。

## 12.5 分组底框

对于内容较多的详情页：

- 每个主要板块使用独立浅灰底框。
- 保持统一圆角。
- 统一内边距。
- 板块之间保持足够间隔。
- 标题和内容有明确层级。
- 不使用大量彩色卡片。
- 不把每个普通字段都单独做成卡片。

目标是让用户一眼能够分清信息区域。

## 12.6 取消常驻说明小字

全局清理以下类型的说明：

- 开发实现解释。
- 数据库规则说明。
- 重复的操作提示。
- 常驻的安全规则解释。
- 已能从状态中明确看出的解释文字。

例如：

`按文件实例管理索引；受保护记录会在预览中说明原因。`

这类文字不应长期占据页面。

对于必要解释：

- 可以通过帮助图标按需查看。
- 操作失败时显示明确原因。
- 危险操作在操作确认时说明影响。

正常情况下页面主要显示业务数据和操作入口。

## 12.7 删除重复状态

同一对象相同含义的状态只显示一次。

例如：

右上角已经显示「已有」，内部不再显示「当前存在」。

但不同含义的业务状态不能错误合并，例如文件存在和二维码启用属于两个维度。

## 12.8 减少不必要的重复操作

同一功能尽量只保留一个清晰入口。

例如批次改名保留左侧编辑入口，不再在每个 PDF 文件行重复显示。

不要因为存在多个页面，就为同一个功能额外增加管理流程。

# 十三、数据安全边界

本次修改不得：

1. 删除真实 PDF 文件。
2. 批量重命名源 PDF。
3. 修改正式图号编码。
4. 释放历史图号占用。
5. 改写旧 BOM 快照。
6. 改写旧外发历史。
7. 覆盖已有二维码网址或业务状态。
8. 自动把不同 SKU 的历史图号合并。
9. 自动把不同外观编码的历史资料混合。
10. 将无法确认的数据强行关联。
11. 因取消前端外观版本 UI 而直接删除底层历史记录。
12. 重新初始化真实业务数据库。

优先通过兼容性迁移、查询修复和界面精简解决问题。

旧数据库迁移后正常读取，现有图号、PDF、BOM、二维码及外发历史不丢失。
